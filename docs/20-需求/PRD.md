# OrchDesk 产品需求文档（PRD）

> 本页是「产品需求」的 canonical 责任方。UI/UX 细节见 [ui-ux.md](ui-ux.md)；技术取舍见 [70-决策](../70-决策/)；分期执行见 [30-开发/PLAN.md](../30-开发/PLAN.md)。
>
> **v1.1 变更**：根据原型 v0.2→v0.6 的收敛反馈重写。核心收敛——导航从 12 项收敛为 3 入口（会话/插件/设置）、会话=一等公民、亮点功能视觉弱化但基于事实执行、一切皆插件、首批 5 内置插件明确。

## 1. 背景

### 1.1 前身 OrchStar 的经验

前身项目 OrchStar（2026-05，本地多 Agent 工作台）已验证产品域可行：Node.js + Hono + SQLite 后端完成 P0–P7（44 个 API、9 DAO、464 测试全通过），覆盖 Agent/模型/技能/提示词/会话/沙箱/授权/上下文八大模块。但它停在半途：

- UI 原型（HTML/JSX）**大部分未接线**到真实 API；
- Electron 桌面壳只开了头；
- 「脑-手解耦」修复路线图停留在 Module 1（主干修复）；
- 自研后端无法提供**可逆热插拔 / 自进化**的运行时保证——这正是新一代 Agent harness 的核心能力。

### 1.2 为什么重建

2026-08 的调研（见 [来源并入记录](../00-项目/source-intake.md)）表明：

- **deepseek-harness（dsh）** 以 Cordis 为内核，把「一切皆插件、注册即 effect、卸载即逆回滚」做成**运行时不变量**，理论地基是《时空可组合性的编程范式》（可逆效应 + 响应式共效应 + 统一 Context）。
- dsh 已具备 OrchDesk 需要的大部分底座能力：append-only SessionEvent 日志与分叉、Profiles+Bundles 分层组合、`agent/pre-step` 必经拦截点、fail-closed approval、沙箱服务抽象。
- dsh **缺的恰好是 OrchDesk 的增量**：桌面壳、跨平台沙箱、系统边界外补偿层、上游意图网关。

**结论：以 dsh 为底座重建 OrchDesk，继承 OrchStar 的产品域与教训，不回迁其代码。**（[ADR-0001](../70-决策/ADR-0001-base-deepseek-harness.md)）

### 1.3 原型收敛过程（v0.2 → v0.6）

原型迭代历经 5 轮用户反馈收敛，最终形态见 `prototype/orchdesk.html`：

| 版本 | 收敛点 |
|---|---|
| v0.1 | 12 页平铺（Dashboard/Agents/Conversations/Orchestration/Skills/Models/Prompts/Memory/Sandbox/Authz/Intent/Settings） |
| v0.2 | **用户反馈「太复杂」** → 收敛为 3 入口（会话/插件/设置），会话=默认落地页；亮点功能视觉弱化；一切皆插件；首批 5 插件明确 |
| v0.3 | 会话侧栏重构：项目分组 + ··菜单 + 悬浮+新建；composer 左下 +/@/授权三件套；插件/设置内页优化 |
| v0.4 | 插件左栏重构为 5 可折叠分组；composer 右侧改模型选择（多选）+ 思维等级 |
| v0.5 | 去掉会话标题专家下拉框；思维等级改为 inline 滑竿 |
| v0.6 | 去掉会话右上角模型名；修复右侧面板收起布局错乱 |

**收敛结论（不可违背）**：3 入口、会话优先、亮点弱化、一切皆插件——这是 v0.6 之后所有后续工作的基线。

## 2. 产品定位

**一句话：本地优先的多 Agent 编排桌面工作台——「个人 Agent 工作室」。**

| 对比 | OrchStar（前身） | OrchDesk（本产品） | dsh（底座） |
|---|---|---|---|
| 运行时 | 自研 Hono+SQLite | dsh / Cordis | dsh / Cordis |
| 形态 | Web 原型 + Electron 半成品 | **桌面应用（Electron）** | CLI / Web |
| 插件能力 | 静态功能堆叠 | **可逆热插拔 + 自进化** | 同左（内核能力） |
| Agent 编排 | 扁平 Agent 列表 | **CEO/Director/Worker 层级 + 可视化**（视觉弱化） | 无（需自建） |
| 意图安全 | 无 | **上游意图网关（DREAM）**（视觉弱化） | 有 `agent/pre-step` 落点 |
| 授权 | 三模式（设计完成） | 三模式 + L0–L4 + fail-closed GUI | approval seam |
| 导航 | 12 项平铺 | **3 入口（会话/插件/设置）** | — |

## 3. 目标用户与场景

**主要用户**：个人开发者 / 独立创作者 / 技术型个人用户——在本机管理多个角色化 Agent，处理开发与创作任务。

**核心场景**：

1. **日常 Agent 助理**：打开应用即进入会话，与当前专家对话，配模型/技能/思维等级，获得 Claude Code 级授权体验。
2. **多 Agent 编排项目**（弱化入口）：需要时通过 composer 的 @ 引用专家/专家团，或到插件页「专家·专家团」分组编排；CEO→Director→Worker 层级在后台执行，GUI 仅在需要时可视化。
3. **安全可控自动化**：Agent 的文件写入、命令执行、网络请求经沙箱与授权门控；外发操作有确认与补偿。
4. **能力热插拔**：随时在插件页安装/卸载技能插件，不重启、不留残留；Agent 可在运行时自建临时工具。

## 4. 设计哲学（继承用户指令，不可违背）

1. **会话=一等公民**：默认落地页是会话，不是 Dashboard。打开应用即可对话，类似 dsh web 形态。
2. **亮点功能视觉弱化但基于事实执行**：脑-手解耦 / 多 Agent 编排 / 意图识别是当前 OrchDesk 的亮点，但不在视觉上喧宾夺主。它们以插件形式存在，在会话中仅以 inline 徽标/提示出现；需要深度操作时进入插件页。
3. **一切皆插件**：模型/沙箱/授权/记忆/编排/意图均以插件形式挂 Cordis ctx；大部分能力收进设置页，不在主导航暴露。
4. **脑-手解耦**：CEO（长驻）负责理解、拆分、分派、回收、Git；Director（8 个领域总监）负责领域规划与验收；Worker（临时）即用即走、完成即销毁、上下文不污染上层。
5. **分层记忆**：全局 / 项目 / 总监 / Worker 四层隔离；Worker 输出须经 Director 过滤才能晋升上层记忆。
6. **Claude Code 级授权体验**：默认安全、分级授权、高风险必确认、决定可审计。
7. **本地优先**：数据与计算不出本机；凭据加密存储。
8. **工程控制论**（钱学森）：目标清晰、状态可观测、反馈闭环、分层控制、扰动下鲁棒。

## 5. 功能需求（FR）

> 优先级：P0=首发必须，P1=重要，P2=增强。分期见 [PLAN](../30-开发/PLAN.md)。
>
> FR 编号在 v1.1 重新排列以反映 3 入口收敛。原 FR-1（Dashboard）降级并入会话页与设置页的状态条。

### FR-1 三入口导航（P0）

- 顶级导航仅 3 项：**会话 / 插件 / 设置**。
- **会话**为默认落地页（应用启动后第一屏）。
- 旧版的 Dashboard / Agents / Orchestration / Memory / Sandbox / Authz / Intent 等 12 项导航**全部取消**；其能力以插件形式收进「插件」页或在「设置」页以开关呈现。
- 导航栏（最左图标列）仅 3 个图标 + 主题切换 + 入门向导入口。

### FR-2 会话页（P0，一等公民）

#### 2.1 会话侧栏（左列）

- **项目分组**：会话按项目归类（如 OrchDesk / 写作助手 / 已归档）；每个项目组可折叠（chevron）+ 会话数 chip。
- **项目头 ··菜单**（hover 才出现）：打开项目目录 / 归档项目（归档走二次确认 modal）。
- **会话项 ··菜单**（hover 才出现）：复制会话 ID / 重命名（modal）/ 创建分支（modal，继承 SessionEvent 前缀）/ 归档。
- **悬浮 + 新建按钮**：侧栏底部居中圆形 + 按钮，hover 弹出「新建会话」气泡 tooltip。
- **已归档**：单独折叠组，含还原入口。

#### 2.2 会话主区

- 标题行：会话名 + 当前专家 badge + 右侧面板折叠箭头（**不显示模型名/会话 ID**，v0.6 收敛）。
- 消息流：用户消息 + Agent 消息（含工具调用展开、step 消耗、触发的授权）。
- **TRACE 反馈**：每条 Agent 消息底部可标记语用意图反馈（正面/负面/中性），脱敏后遥测至公开 GitHub 仓库（FR-7 TRACE 插件）。
- **SubAgent 芯片**：脑手解耦派发的 SubAgent 以 inline 芯片呈现（W-xxx 临时任务 · 执行中/已回收）。
- **右侧上下文栏**（可折叠）：选中会话的属性、事件、授权请求内联；收起时 `display:none` 完全移出布局流（v0.6 修复），主区占满剩余空间。

#### 2.3 composer（输入区）

- **左下三件套**：
  - `+` 加载技能：modal 列出已装插件 + 技能市场项，注册为本次会话 effect，离开会话即卸载。
  - `@` 引用专家或专家团：modal 列出 8 专家 + 3 团，以 SubAgent 形式参与本次回复，不替换主会话。
  - **授权芯片**：默认「工作空间写」（绿点）；点击升级 → 弹二次确认 modal 警示 L4 不可逆 → 确认后切到「FULL ACCESS」（warn 橙 + pulse）；再点可降级。
- **右下控件**：
  - **模型选择**：按钮显示当前已选模型，多选时显示「N 个模型」；点击弹 modal，按提供商分组（Anthropic / OpenAI / DeepSeek / Ollama 本地），支持多选、全选/取消全选、清空。
  - **思维等级**：inline range slider（0-3 对应 关闭/标准/深度/最大），拖动实时切换，**不弹 modal**（v0.5 收敛）。
  - 意图识别状态点 + 发送按钮。
- 发送时 toast 回显「N 模型 · 思维 等级」。

### FR-3 插件页（P0，一切皆插件）

#### 3.1 左栏 5 可折叠分组

| 分组 | 内容 | 计数 |
|---|---|---|
| 内置插件 | 首批 5 插件（见 FR-7） | 5 |
| 插件市场 | Git / PDF / 浏览器 / 邮件 / 可视化 等可安装插件 | 5+ |
| 技能市场 | 观雅集市场（guanji / consolidate / aihot / kimi-webbridge 等） | 4+ |
| 专家·专家团 | 8 专家 + 3 团（类 WorkBuddy 专家团模型） | 11 |
| 连接器 | GitHub / 飞书 / 企微 / 腾讯文档 / Notion / Linear / TAPD / 钉钉 | 8+ |

- 每组 chevron 折叠/展开 + 计数 chip；默认全部展开。

#### 3.2 主区

- 每个插件卡片：名称 + 能力声明 chip 行（如 `github.write` / `agent.dispose` / `memory.commit`，高风险能力标 warn 橙）+ 启用/停用开关。
- **配置内联展开**：点配置按钮 toggle 卡片展开，显示配置项 + 审计日志 + 卸载并回滚按钮。
- **热插拔**：启用 = 注册 effect，停用 = 注册回滚（无残留），不重启。
- 技能市场项：需授权的标「需授权」徽标，安装走 FULL ACCESS 二次确认。

### FR-4 设置页（P0）

#### 4.1 顶部 4 格状态条

一眼看完的关键状态：授权模式 / 沙箱 backend / 数据目录 / 运行时。

#### 4.2 分组

- **模型管理**（FR-5）：提供商分组表 + search input（按名称/提供方）+ 测试连通性按钮。
- **沙箱**（FR-8）：backend 选择 + 白名单目录 + 日志入口。
- **授权**（FR-9）：模式切换 + L0–L4 行为矩阵 + 永久授权白名单（可撤销）+ 审计日志。
- **桌面集成**（2×3 网格）：系统托盘 / 全局快捷键 / 登录自启动 / 自动更新 / 悬浮窗 / 开机提醒。
- **数据目录**：路径 + 打开目录 + 导出快照 + 内容清单（sessions.db / memory / plugins / logs）。
- **凭据**：AES-256-GCM 加密存储，掩码显示。
- **关于**：版本号卡片化。

### FR-5 模型管理（P0）

- 多提供商注册（Anthropic / OpenAI / DeepSeek / 本地 Ollama / 自定义端点），API Key **AES-256-GCM 加密存储**（密钥派生自机器指纹，继承 OrchStar 设计）。
- 按 Agent/会话绑定、即时切换；上下文窗口/输出上限参数化；用量追踪（可选）。
- 会话 composer 支持跨提供商**多选模型**（多模型协同推理）。

### FR-6 会话与分叉（P0）

- 多会话管理；消息流实时推送。
- **SessionEvent append-only 日志**：模型可见必入日志（dsh 不变量），支持**分叉（fork）**、回放、上下文重建。
- 分叉点在消息流中以节点标记；回放视图从日志重建只读时间线。

### FR-7 首批 5 内置插件（P0/P1）

| 插件 | 优先级 | 能力 |
|---|---|---|
| **意图识别** | P0 | 配本地模型（qwen3:14b 起步），挂 `agent/pre-step`，实现 DREAM F1–F4 Funnel + M1/M2/M3 + 4-gate + default fallback（[ADR-0003](../70-决策/ADR-0003-intent-gateway-pre-step.md)）。决策：ACT 放行 / CONFIRM 弹确认 / BLOCK 拒绝（入日志）。 |
| **TRACE** | P0 | Agent Loop 前 + Loop 结束，记录语用意图的用户反馈，脱敏遥测上传到公开 GitHub 仓库。会话中每条 Agent 消息底部可标记反馈。 |
| **脑手解耦** | P1 | 主会话（CEO）负责理解、回收、沉淀；SubAgent（Worker）执行、反馈、即用即走。SubAgent 以 inline 芯片呈现，完成后销毁、上下文不污染上层。 |
| **多 Agent 编排** | P1 | 类 WorkBuddy 的专家 / 专家团，可使用预置（8 专家 + 3 团），也可以自己编排。CEO→Director→Worker 层级在后台执行。 |
| **OrchClaw Hub** | P2（延后） | 配对后可通过主会话控制远程 Agent。需联调，首发不含。 |

### FR-8 沙箱（P0）

- 文件写入限定白名单目录；命令执行白名单 + 参数检查；网络请求域名白名单；代码执行进程级隔离。
- **跨平台 backend**：Windows（ACL，先行）→ macOS（sandbox-exec/独立 helper）→ Linux（复用 `landlock-run`）。沙箱必须靠外部机制（论文 §6.3），不接受纯语言级拦截。
- 沙箱日志可检索（设置页入口）。

### FR-9 授权（P0）

- 三种模式：`default`（沙箱通过自动执行、阻塞弹授权）/ `trusted`（自动通过，高风险仍二次确认）/ `paranoid`（逐项确认）。
- 操作分级 L0–L4（只读/本地修改/系统影响/网络/破坏性），L3/L4 任何模式都需确认，L4 二次确认。
- 授权粒度：单次 / 会话 / 永久（操作类型+路径白名单，可查看可撤销）。
- **fail-closed**：审批应答缺失/异常一律不开门（复用 dsh approval seam）。
- 全部授权决定记审计日志。
- 会话 composer 的授权芯片是日常入口（工作空间写 ↔ FULL ACCESS），深度配置在设置页。

### FR-10 上下文转储与分层记忆（P1）

- 达到上下文阈值（默认 80%）自动转储：LLM 摘要 → 语义分块 → 本地向量编码（TF-IDF 起步）→ 伪记忆注入。
- 提到相关内容时语义召回 Top-K 注入。
- **分层记忆**：global / project / director / worker 四域隔离（FR-哲学落地）；Worker 输出须经 Director 过滤才能晋升上层。

### FR-11 系统提示词库（P1）

- 提示词与技能解耦；分类（角色行为/安全边界/输出格式/技能联动）；`{skill:xxx}` 引用语法；按 Agent 绑定与优先级合并。

### FR-12 系统边界外补偿层（P1，OrchDesk 特色）

- 边界外 emission（发消息 / 发网络请求 / 写共享文件）**不可逆**（论文 §6.1），Cordis 无法撤销。
- OrchDesk 自建补偿层：发送前二次确认（withhold）、发送后撤回/补偿动作（删文件、撤回消息等），补偿动作入审计日志。
- 三类高危（删除文件 / 对外发送 / 不可逆操作）默认 CONFIRM。

### FR-13 自进化（P2）

- 创造模式：Agent 运行时自建/卸载**临时插件**（信任级 = Shell、仅驻内存、重启即失），用于一次性工具。
- 自生成插件须经更强静态分析与授权门控（论文遗留开放问题，OrchDesk 以保守策略落地：默认 CONFIRM + 沙箱内运行）。

## 6. 非功能需求（NFR）

| 类别 | 要求 |
|---|---|
| 本地优先 | 全部数据存本机（SQLite/JSONL/文件）；无云端依赖；离线可用（除模型 API 调用本身） |
| 安全 | 凭据 AES-256-GCM；沙箱外部机制；approval fail-closed；插件加载期能力审查（Cordis `inject` 静态声明） |
| 可观测 | SessionEvent 全量日志；授权/补偿审计；编排反馈信号可视化 |
| 性能 | 桌面冷启动 < 5s；会话消息渲染流畅；大列表分页/虚拟化 |
| 可移植 | Windows 首发；macOS / Linux 随后（沙箱 backend 是主要平台工作） |
| 可恢复 | 插件卸载无残留（可逆效应）；会话可重放重建 |

## 7. 非目标（明确不做）

- 不做云端集群 / 多人协作服务端（保持个人本地定位）。
- 不做模型训练 / 微调。
- 不做移动端。
- **不恢复 12 项导航**：3 入口是收敛结论，不在主导航重新暴露 Dashboard/Agents/Orchestration 等独立页。
- 首发不做技能市场完整生态（P2 接入观雅集即可）。

## 8. 成功度量

| 指标 | 目标 |
|---|---|
| 底座可运行 | dsh 桌面 bundle 启动并跑通一次端到端会话 |
| 迁移完整度 | OrchStar 八大模块在 OrchDesk 全部可用（以插件形式） |
| 3 入口闭环 | 会话/插件/设置三页全部接线真实能力，无空壳页 |
| 安全门禁 | L3/L4 操作 100% 经授权；边界外 emission 100% 经确认或补偿 |
| 编排可用 | 完成一次 CEO→Director→Worker 三层任务闭环（后台执行，需要时可视化） |
| 热插拔 | 技能插件安装/卸载不重启、无残留（可逆效应验证） |
