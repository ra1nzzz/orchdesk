# 开发工作流与 SOP

> 本页是「开发协作流程」的 canonical 责任方。任务 SOP 继承用户既定指令；知识库治理遵循 `consolidate-project-knowledge-base` SKILL。

## 1. 任务执行 SOP（继承用户指令）

1. **接任务**：启动任务审计子代理，理解并记录任务需求与目标。
2. **定策略**：主会话按复杂度决定单线完成或多子代理并行开发。
3. **开发**：按 [PLAN](PLAN.md) 的阶段与模块实施。
4. **三方 review**：开发完毕启动 3 个子代理**并行** review——代码质量 / 代码效率 / 代码可复用性。
5. **修复优化**：主会话汇总 review 结果，安排修复（可视情况多子代理并行）。
6. **对比审计**：召回任务审计子代理对优化后代码做对比审计，确认符合需求。
7. **提交**：通过后在**用户明确授权**时提交；汇总汇报并给出下一步建议。

## 2. 提交规范

- **原子提交**：一个模块/Phase 一个或多个原子提交；知识迁移与代码改动**分开提交**。
- 提交前过门禁（见 [40-质量](../40-质量/quality-gates.md)）：typecheck + test + 知识库 audit。
- 提交信息含动机与影响面；引用相关 ADR / FR。

## 3. 知识库治理规则（本 docs/ 的维护）

1. **唯一入口**：根索引 [../README.md](../README.md)；不得另立竞争入口。
2. **canonical 唯一**：每类事实只有一个责任方（映射表见 [当前状态](../00-项目/current-state.md)）；其它副本标记为镜像/快照。
3. **当前 vs 历史**：当前事实写 canonical 页；过期背景进 [99-归档](../99-归档/index.md)，不得把旧计划写成现在时。
4. **禁入共享库**：密钥/令牌/机器凭据/生成二进制/本机绝对路径/瞬时证据，一律不进 `docs/`。
5. **冲突显式裁决**：记录冲突、选定权威、被否定解释与理由（见 [conflicts](../70-决策/conflicts.md)），不静默拼接。
6. **机器验收**：改动后运行 `audit_knowledge_base.py`（见质量门禁）。
7. **来源并入**：新引入外部资料先登记 [来源并入记录](../00-项目/source-intake.md)（含 commit/tree 快照与 disposition）。

## 4. dsh 基线管理

- 底座基线锁定在 `references/deepseek-harness` 的指定 commit（当前 `99f6f02`，见来源并入记录）。
- 升级基线属架构变更：须开 ADR、记录新旧 commit、回归验证后再切换。
- 自定义改动走 `cordis.patch.yml` 补丁层，不直接改 vendor 源码。

## 5. 分支与工作树纪律

- 不删除默认分支或版本 tag；遵守受保护分支流程。
- 清理分支/工作树前，先在归档记录 tip commit/tree 与未提交制品的可恢复性（参考前身 OrchStar 的脏工作树教训：其未提交的 fix 脚本与 smoke 截图删除后无法从 Git 恢复）。
- 文档整理不合并无关仓库历史，保持各来源历史独立。
