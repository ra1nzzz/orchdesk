# OrchDesk PRD 差距盘点（v0.3.1 时点）

> 对照 [PRD v1.1](../20-需求/PRD.md) 逐条评估真实实现度。
> 判定口径：**「已接线」= 有真实数据流（落盘 / 调主进程 / 调外部 API）**；
> 「半接线」= UI 在但数据是硬编码常量或只改前端 state；「未实现」= 无 UI 或点击无效果。
> 所有结论均由只读审计 + 抽样复核得出，证据精确到行号。

## 0. 一句话结论

**PRD 整体完成度约 30–35%。桌面壳可用，但产品真正的差异化能力（插件体系）是「写完了没接线」的死代码。**

分两层看：
- **桌面壳层（Electron + 渲染层 + 模型调用）**：约 60–65% —— 会话 CRUD 落盘、真实模型调用与工具循环、模型配置持久化、观雅集/Hub 接入、打包发布，这些都是真代码。
- **产品能力层（PRD 的 FR-7 至 FR-13）**：约 0–10% —— 9 个 Cordis 插件共 2515 行源码、verify-p5 全绿，但**从未被 Electron 加载**。

## 1. 根因：dsh/Cordis 运行时完全缺席

这是所有缺口的共同源头，不是各自独立的 bug。

| 证据 | 位置 |
|---|---|
| `apps/` 下无任何 dsh/cordis 的 import（只有注释） | `main.ts:29/32/721/796-798` |
| desktop 依赖仅 `marked` + `png-to-ico`，无 `@orchdesk/dsh-*` | `apps/desktop/package.json` |
| 打包产物 asar（90 文件）中 dsh/cordis/plugin/deepseek 命中 **0** | `release/win-unpacked/resources/app.asar` |
| 授权桥被显式注入空 ctx | `main.ts:957` `initAuthzBridge({ get: () => undefined })` |
| 11 个 IPC handler 统一返回静态占位 + warn | `main.ts:800-846` |

**后果**：`packages/plugin/*` 的 2515 行实现（意图识别 DREAM F1–F4+M1–M3+4-gate、TRACE 脱敏遥测、脑手解耦、多 Agent 编排、四域记忆 TF-IDF、提示词库、补偿层、自进化）在应用内**一个都跑不到**。

## 6. 若要补齐，最小代价路径

差距看似很大，但**不是要重写**——2515 行插件实现已经写好并通过验证，缺的是「接上」。

1. **接入 dsh/Cordis 运行时**（解锁 FR-7/9/10/11/12/13 六项，收益最大）
   - 阻塞点：desktop 是 CJS（`tsconfig.json:6`），插件输出 ESM，需统一模块格式或走 bundle
   - 步骤：workspace 引入 dsh → 主进程 `new Context()` 装载 desktop bundle + 9 插件 → 用真实 ctx 替换 `main.ts:957` 的占位 → 11 个 stub 改为 `ctx.get(...)` → electron-builder `files` 补依赖树
2. **修 6 处功能性缺陷**（约半天，收益立竿见影）
3. **真实沙箱**（进程隔离 + Windows ACL）与 **AES-256-GCM + 机器指纹** 加密（对齐 PRD NFR）
4. **清 mock 数据**：`EXPERTS` / `TEAMS` / `PLUGINS` / `PLUGIN_MARKET` / `CONNECTORS` / `mcps` 六个常量改为插件真实注册数据
5. **测试覆盖**：`verify-p5.mjs` 只覆盖 2 个插件，其余 7 个零测试

## 7. 本盘点未覆盖

- 性能 NFR（冷启动 < 5s、大列表虚拟化）未实测
- macOS / Linux 沙箱 backend（PRD 明确 Windows 首发，属计划内延后）
- GUI 实机冒烟（本环境无法启动 Electron，BUG-W02）
